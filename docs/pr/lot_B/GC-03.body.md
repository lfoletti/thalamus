## Description

### Problem
A key is confined to one `user_id`, one `scope`, one `namespace` and one `collection`. An agent that reads its team's collection and its own needs two keys and two connections, which a client holding one key cannot do. The only alternative is an unconfined key.

### Fix
`Scope` gains `user_ids`, `scopes`, `namespaces` and `collections` beside the singular fields. The two forms add up into one constraint per field, so `{"collection":"a","collections":["b"]}` means a or b. A request still names exactly one value, which must be among the key's. The gRPC request check, the REST body check and the two row-ownership checks share the membership rule through one function, so no surface can disagree. A denial spells out the whole list. An empty string inside a list is a key-file error, reported when the key set loads.

Keys written with the singular fields behave exactly as before.

### Tests
- `pkg/authz/authz_test.go`: a two-collection key permits each listed value and refuses another; singular and plural add up; an empty list value is a load error; the denial names the list.
- `pkg/rpcserver/scoped_keys_test.go`: a key confined to two collections saves and searches in each over gRPC, is refused a third, and reads its own row by id.
- `go vet` and `go test -race ./...` pass.
