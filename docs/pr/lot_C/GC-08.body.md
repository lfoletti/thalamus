## Description

### Changes since review (20 October 2026)

Each point has a test that was written first and fails without the change (`pkg/cortexdb/graphrag_ingest_review_test.go`).

1. **Dedupe is per collection.** `documentWithContentHash` takes the collection and answers only with a document whose chunks sit in it, so the same page may be kept once per collection and `duplicate_of` never names a document of another one (`TestDedupeIsDecidedWithinTheCollection`).
2. **"Unchanged" is exact.** The record now carries the chunking it was made with (`chunk_size`, `chunk_overlap`, resolved values, next to `content_sha256`), and the unchanged check also compares the collection the chunks sit in. Another chunk size or another collection is a re-ingest (`TestAnUnchangedReingestMeansTheSameCollectionAndTheSameChunking`).
3. **The hash follows the content on every write path.** `knowledge_update` recomputes the three marks when it rebuilds the chunks and keeps them on a metadata-only update; `knowledge_save` sets them too, and puts the hash on the document node where dedupe looks, so a document saved either way is seen (`TestTheContentHashFollowsTheContentThroughKnowledgeWrites`). A record written before the marks existed gets them on its next update.
4. **One transaction.** `ingest_document` builds the same mutation plan as `knowledge_save` and applies it through `applyKnowledgeMutation`: record, chunks, nodes and edges land together or not at all, and a re-ingest retires the chunks and nodes of the previous text, so a shorter text leaves no chunk past its end (`TestAnIngestWritesEverythingOrNothing`, with a `RAISE(ABORT)` trigger on the chunk table). This also means a re-ingest archives the previous graph of the document, as `knowledge_save` does.
5. **Chunk order.** The ids of an unchanged re-ingest come in `chunk_index` order, not text order, which parts at the thousandth chunk (`TestTheChunkIDsOfAnUnchangedReingestComeInChunkOrder`, 1001 chunks).

Rebased on v2.134.1.

### Problem
A sync job that follows sources has two questions on every pass: has this document changed since it was stored, and is this content already stored under another id. Neither could be answered without re-reading the brain, and re-ingesting an unchanged document rewrote every chunk and node.

### Fix
- `ingest_document` keeps the content's SHA-256 as metadata `content_sha256` on the record, on the document node and on each chunk, and returns it in the response; `knowledge_save` and `knowledge_update` keep it too. The record also carries the chunking (`chunk_size`, `chunk_overlap`).
- A re-ingest that says exactly what is stored (same hash, title, source, author, metadata, chunking and collection) writes nothing and reports `unchanged`, returning the existing ids in chunk order. Any difference is a real re-ingest, written in one transaction with the chunks and nodes of the previous text retired.
- With `dedupe: true`, content already held by another document of the same collection is not stored again; the response names it in `duplicate_of`. The lookup asks the document node for its hash property through Cypher rather than scanning the records table, then the holder's chunks for its collection.

Nothing changes for a caller that ignores the new fields: an ingest with different content behaves as before, in one transaction.

### Tests
- `pkg/cortexdb/graphrag_ingest_review_test.go`: the five tests above.
- `pkg/cortexdb/graphrag_ingest_dedupe_test.go`: the hash is kept on record, node, chunks and response; an identical re-ingest writes nothing and reports `unchanged`; a changed re-ingest, or one that drops a metadata key, rewrites; `dedupe` names the holder of the same content and stores nothing, never the document itself; without `dedupe` the duplicate is stored; on a closed brain, with the chunk table unreadable, with the collections table unreadable or with the graph unreadable, a re-ingest and a dedupe check report the failure.
- `go vet` and `go test -race ./...` pass.

**Failing first.** The tests use new fields, so the proof is per rule: disable it, keep the package compiling, and a test must fail. Eight mutations for this amendment, eight killed: dedupe answering across collections; the chunking not stamped; the collection not compared; an update that keeps the old hash; a save without a hash; the hash left off the node on save; a re-ingest that does not retire the previous chunks; chunk ids sorted by text. The mutations of the first version still hold, replayed on the head of the stack. Every line of the patch has a test.

Part of a small series on running one CortexDB server for several teams (see discussion #66, batch 3).

## Performance Impact
One SHA-256 of the content per write, one record read and one chunk listing for the `unchanged` check. With `dedupe`, one Cypher lookup by hash and one chunk read per candidate. The ingest itself now runs in one transaction, like `knowledge_save`.

## Breaking Changes
None. One new optional argument, two new response fields, three new metadata keys (`content_sha256`, `chunk_size`, `chunk_overlap`) on documents written through `ingest_document`, `knowledge_save` and `knowledge_update`.
