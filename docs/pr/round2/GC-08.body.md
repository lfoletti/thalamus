## Description

### Changes since the second review (21 October 2026)

Each point has a test that was written first and fails without the change (`pkg/cortexdb/graphrag_ingest_round2_test.go`, `pkg/cortexdb/graphrag_ingest_postgres_test.go`). The same scenarios now run on `main` and on this head before I push, so that a re-ingest does here what it does on `main` unless this body says otherwise.

1. **A re-ingest keeps the graph the caller attached.** What a re-ingest does depends on the text. The same text, chunked the same way, into the same collection, is written in place: the record, the document node and the chunks are upserted under their ids, and the entities, the mention edges and the relations are not touched. Other text keeps the chunk ids that survive, upserted in place with the graph attached to them (chunk *i* of the new text is chunk *i* of the old one, as on `main`), and retires only the chunks past the new text's end, with the edges that hang off them (mention, next), so none of them is served again; the entities and the relations stay. After a title-only re-ingest, entities, relations and `search_chunks_by_entities` count what they counted before, as on `main` (`TestATitleOnlyReingestKeepsTheGraphTheCallerAttached`, `TestAContentChangeReplacesTheChunksAndKeepsTheEntities`). `knowledge_save` over an existing id stays a rewrite, as on `main`: the chunks and the graph of the previous text are retired first (`TestAKnowledgeSaveOverAnExistingIdRetiresWhatTheOldTextLeft`). `knowledge_update` stays a rewrite too, also for a title alone, as on `main`: its plan always runs the heuristic extraction and the default chunking, so keeping the graph there would need its own change, which I would rather propose apart. Chunk *i* keeps its graph whatever its new text says, as on `main`: after other text, a mention edge can name an entity the chunk no longer mentions, and a relation's `chunk_ids` can name a retired chunk, until the caller re-attaches its graph. The differential scenarios (the same test file run on `main` and on this head) differ on one point only: after other, shorter text, `main` keeps the chunk rows and chunk nodes past the new text's end, with their edges, this head does not; what the surviving chunk reaches is the same on both.
2. **"Unchanged" means the stored copy is whole.** It is said only when the record says what the request says and the chunk rows and the chunk nodes are all there. One missing chunk row of three is enough to rebuild them (`TestUnchangedNeedsEveryChunkRow`). The marks on the record and the hash on the document node describe the chunks `knowledge_save` and `knowledge_update` stored (`TestTheMarksDescribeTheStoredChunks`), and a chunk retired by a shorter text is recorded in history as a re-ingest (`TestARetiredChunkIsRecordedAsAReingest`). After `delete_document_graph`, the same text rebuilds the nodes, as `main` does (`TestUnchangedIsSaidOnlyWhenTheChunkNodesAreThere`).
3. **Dedupe.** The lookup runs inside the write transaction, under the same write lock as the insert (on PostgreSQL, an advisory transaction lock on the hash), so concurrent dedupe ingests store one copy (`TestTwoConcurrentDedupeIngestsStoreOneCopy`, 25 rounds of four goroutines started together, because one round can pass by luck with the lookup in its own transaction; `TestTheIngestPathsHoldOnPostgres`). It has no row cap: the copy is found past sixteen holders in other collections (`TestDedupeFindsTheCopyPastSixteenHolders`, 17 holders). Among several holders of the collection, it names the smallest id (`TestDedupeNamesTheSmallestHolder`). An expression index on `_content_sha256` serves the lookup on both stores (`idx_documents_content_sha256`, the same guarded expression as the query; `TestTheDedupeLookupUsesTheContentHashIndex` reads the SQLite plan). Here every document holds its content; #76 adds its expiry predicate to the same query, so an expired document does not. A proposed or rejected document still holds it under the review gate of #77: dedupe is about content, not visibility. A document written by `InsertGraphDocument` carries no marks, since its record has no metadata: it is never `unchanged` and holds no content for dedupe, and the next ingest over its id stamps the marks again (`TestADocumentWrittenWithoutTheMarksIsNeitherUnchangedNorAHolder`). Two limits, named: on SQLite the write lock is this process's queue, so two processes writing one file can both store the content, or one gets `SQLITE_BUSY`, where PostgreSQL's advisory lock holds across processes; and `dedupe` on an id that already exists with other content, when another document holds the new content, answers `duplicate_of` and leaves the old record as it is.
4. **A confined key may send `dedupe`.** Rebased on v2.136.0, which has the allowlist of #72: `dedupe` is classified there as data on `ingest_document`, and the lookup stays in the key's collection, so `duplicate_of` never names a document of another collection (`TestAConfinedKeyDedupesWithinItsCollectionOnly`, over REST).
5. **The marks never overwrite a caller's key.** The content hash and the chunking live under the engine's own keys, `_content_sha256`, `_chunk_size` and `_chunk_overlap`, with the leading underscore importflow already uses for `_table`; a caller's `content_sha256` or `chunk_size` is stored as it came, and a caller's copy of the engine's keys is dropped (`TestTheIngestMarksNeverOverwriteACallersKey`).
6. **A confined key can send back a document it read.** Every document now carries the marks, which start with `_`, and the allowlist of #72 refuses a `_` key from a confined key. Every write of a document's metadata (`ingest_document`, `knowledge_save`, `knowledge_update`, and their typed routes) writes the three marks over the caller's (`cortexdb.EngineDocumentKeys`), so the allowlist lines of those three tools take them back under their exact spelling. Without that, a confined key that read a document and sent its metadata back got `403` where `main` answers `200`, on the tool route and on the typed routes (`TestAToolWriteTakesTheMarksTheFacadeReplaces`, `TestATypedKnowledgeWriteTakesTheMarksTheFacadeReplaces`, on both ports, every mark forged and the engine's kept; `TestTheRewrittenMarksPassOnTheDocumentWritesOnly` for the allowlist rule itself). `InsertGraphDocument` writes no mark: its record has no metadata, and it now drops a caller's copy of the marks from the metadata it puts on the chunks, so the metadata read back passes there too, as on `main`, and no stale mark lands on chunks it does not describe (`TestInsertGraphDocumentDropsACallersCopyOfTheMarks`; on `main` a caller's `_content_sha256` was stored on the chunks like any key). Another spelling of a mark, another engine key such as `_table`, and a memory write keep the refusal. A signed record keeps the refusal of `written_by` on the tool route, as on `main`.

Also: an ingest whose retire step cannot complete, or whose write transaction fails, is reported and writes nothing (two tests with `RAISE(ABORT)` triggers); an unreachable guard on an empty chunk list is gone. Two re-ingests of one id at the same time read the stored version outside the transaction, as on `main`, and can store the same version number. Rebased on v2.136.0. 415 lines outside tests over 12 files, 70 removed.

### Problem
A sync job that follows sources has two questions on every pass: has this document changed since it was stored, and is this content already stored under another id. Neither could be answered without re-reading the brain, and re-ingesting an unchanged document rewrote every chunk and node.

### Fix
- `ingest_document` keeps the content's SHA-256 under the metadata key `_content_sha256` on the record, and returns it in the response; it copies the marks onto its document node and its chunks, as it copies every metadata key. `knowledge_save` and `knowledge_update` keep the hash on the record and on the document node. The record also carries the chunking (`_chunk_size`, `_chunk_overlap`). These keys are the engine's: written from the content, never from the caller.
- A re-ingest that says exactly what is stored (same hash, title, source, author, metadata, chunking and collection), with its chunks and chunk nodes in place, writes nothing and reports `unchanged`, returning the existing ids in chunk order. The same text with another title or metadata is written in place, graph untouched. Other text upserts the surviving chunk ids in place, retires the chunks past its end and keeps the entities and relations. Each of these is one transaction.
- With `dedupe: true`, content already held by another document of the same collection is not stored again; the response names it in `duplicate_of`. The lookup runs in the write transaction, on an expression index.

Nothing changes for a caller that ignores the new fields.

## Performance Impact
One SHA-256 of the content per write. A re-ingest over an existing id reads the record; only when it says what the request says does the `unchanged` check also read the chunk rows, the first chunk and the chunk nodes (three more reads). With `dedupe`, one indexed lookup by hash inside the write transaction; the index costs one entry per document. On PostgreSQL the dedupe ingest takes an advisory transaction lock on the hash, so two ingests of the same content serialize; ingests of different content do not.

## Breaking Changes
None. One new optional argument, two new response fields, one new index, three new metadata keys (`_content_sha256`, `_chunk_size`, `_chunk_overlap`) on documents written through `ingest_document`, `knowledge_save` and `knowledge_update`. The keys of the first version (`content_sha256`, `chunk_size`, `chunk_overlap`) were never released. A caller that sent its own `_content_sha256`, `_chunk_size` or `_chunk_overlap` in metadata now has the engine's value instead, or nothing on the chunks of `InsertGraphDocument`, which writes no mark; its other keys, other spellings and other `_` keys stay (point 6).
