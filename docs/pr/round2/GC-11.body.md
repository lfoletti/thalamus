## Description

`POST /v1/knowledge` and `POST /v1/memory` write the row their id names, and create it when the id names nothing, as `SaveKnowledge` and `SaveMemory` do over gRPC. For a confined key, the gRPC side reads that row first and refuses one outside the key's scope (`guardKnowledgeUpsert`, `guardMemoryUpsert` in `pkg/rpcserver/ownership.go`). The REST side checked the scope fields of the body only, so an id that named another scope's row reached the upsert: the row was overwritten and moved into the caller's scope. This has been the case since the REST policy came in (v2.91.0).

`POST /v1/memory` also takes `supersedes`, which the gRPC message does not. Each target is marked retired (`superseded_by`), with no scope check, so a confined key could retire another user's memory, and a missing target answered differently from a foreign one.

Both upsert guards, REST and gRPC, also took an id of blanks for no id, while the facade stores it as given: a confined key could take another scope's row named `" "`, through `SaveKnowledge`, `UpdateKnowledge` or `SaveMemory` over gRPC and the two routes over REST.

Independent of the other open PRs: based on `main`, touches `pkg/httpapi` and two lines of `pkg/rpcserver`.

### Fix
The REST policy guards the rows an upsert route names, for a confined key, before the handler runs (`pkg/httpapi/upsert.go`):
- The row is read by id, under every spelling of the id field, since `encoding/json` reads any of them into the request.
- A row outside the key's scope is `404`, worded as the gRPC side words it (`knowledge "<id>" not found`), and is left as it was.
- An id that names nothing is a create and passes; the scope fields of the body already confine what it creates. Only an empty id is skipped, as the facade refuses only that one; no id leaves the route its own answer (`knowledge_id is required`).
- Each `supersedes` target must be a memory the key may have. The new memory and its targets are read as the handler decodes them, so they are the ones `SaveMemory` sees, whichever spelling the body uses. A foreign target and a missing one get the same `404` (`supersede "<id>": not found`), before anything is written, so no new memory is left behind. The targets `SaveMemory` skips (blank, or the new memory itself) are skipped here too.
- Only the facade's not-found sentinel (`core.ErrNotFound`) means a missing row. Any other read failure is `500`, never a pass.
- The row rules are the gRPC side's, field for field: a document is the key's when its collection is, and a key confined on a memory field reaches no document; a memory is the key's when its user, scope and namespace are, and a collection-confined key reaches no memory. Rows nobody owns follow the same rule: a memory of the global bucket is not a user-confined key's, and a document saved with no collection, in the default one, is not a collection-confined key's.

On gRPC, `guardKnowledgeUpsert` and `guardMemoryUpsert` now skip only an empty id. One difference stays, as on `main`: when their first read says not found, they read again to tell a create from a foreign row, and a failure of that second read lets the create through. The first read has already reported any other failure, so I left it; I can align it if you prefer.

Unconfined keys are not checked, and no other route changes. The guard runs before the handler, so for a confined key its `404` comes before the handler's own `400`s: a foreign id with empty content, or a foreign or missing target in a body with no `memory_id`, now gets `404` where `main` answered `400`. The guard reads, then the handler writes; the window between the two is the one the gRPC guards already document.

### Scope
- `entities` and `relations` in a typed upsert write shared graph nodes. That is the graph-write class, which #73 and #74 close for confined keys on both ports (a typed write takes what the allowlist line of its tool takes); this PR leaves it to them.
- #72 makes the facade hold a foreign `supersedes` target as not found under a caller scope. With both merged, the REST check of the targets stays as the port's own answer, as on the other rows.
- Wording: the typed routes answer as the typed RPCs do (`knowledge "<id>" not found`); the tool route in #74 answers as the tool does. #74 also adds a line to the same block of `authorizeWith`; whichever lands second, I rebase it.
- The row rule now lives in the facade's callers on each port. Moving it into `SaveKnowledge` and `SaveMemory`, under `CallerScope`, would hold it in one place; that is a larger change than this fix, and I can follow up with it if you want it there.

## Performance Impact
For a confined key, one `GetKnowledge` or `GetMemory` per upsert, and one `GetMemory` per `supersedes` target; `GetKnowledge` loads the document's chunks, so its cost grows with the document. Nothing for an unconfined key.

## Breaking Changes
None for an unconfined key. A confined key that named another scope's row in an upsert, an id of blanks included, or another scope's memory in `supersedes`, now gets `404` instead of writing it. A confined key's missing `supersedes` target is `404` before the write, so no new memory is left behind.
