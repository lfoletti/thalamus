## Description

`InsertGraphDocument` writes the document its id names, and creates it when the id names nothing, as `SaveKnowledge` does. For a confined key, `SaveKnowledge` and `UpdateKnowledge` read that document first and refuse one outside the key's scope (`guardKnowledgeUpsert` in `pkg/rpcserver/ownership.go`). `InsertGraphDocument` did not: a key confined to `notes` could call it with the id of a document in `secrets`, and the document was overwritten and moved into `notes`. A collection-confined key reaches this RPC because its request carries `collection`.

Independent of the other open PRs: based on `main`, touches `pkg/rpcserver` only.

### Fix
`InsertGraphDocument` goes through the same guard as `SaveKnowledge`, before the facade runs:
- A document outside the key's scope is `NOT_FOUND`, worded as the other typed RPCs word it (`knowledge "<id>" not found`), and is left as it was.
- An id that names nothing is a create and passes; `collection` already confines what it creates.
- Unconfined keys are not checked.

One hole stays until #82 lands. `guardKnowledgeUpsert` takes an id of blanks (`" "`, `"\t"`) for no id, while the facade stores it as given, so a confined key can still overwrite another collection's document named `" "` through this RPC, as through `SaveKnowledge` today. #82 makes the guard skip only an empty id, which closes it here too; I will add a blank-id case for `InsertGraphDocument` to whichever of the two lands second.

### Scope
- The class is every typed RPC a confined key reaches that names a row by id. From the protos, the others are already guarded on `main`: `SaveKnowledge`, `UpdateKnowledge` and `SaveMemory` by the upsert guards, and `GetKnowledge`, `DeleteKnowledge`, `GetMemory`, `UpdateMemory` and `DeleteMemory` by their handlers. The searches (`SearchGraphRag`, `SearchText`, `SearchKnowledge`, `SearchMemory`) carry a scope field and are reachable, but they name no row by id. Every other RPC carries no scope field, so `AuthorizeRows` refuses it to a confined key.
- #73 withholds a document whose chunks are gone from a confined key on the typed RPCs. With both merged, `InsertGraphDocument` gets that rule through the guard; I will add its test case to whichever of the two lands second.

### Tests
`pkg/rpcserver/ingest_ownership_test.go`, `TestInsertGraphDocumentCannotTakeADocumentOfAnotherCollection`:
- A key confined to `notes` naming a document of `secrets` gets `NOT_FOUND` `knowledge "sec" not found`, and the document reads back unchanged, in `secrets`.
- The same call with empty content is `NOT_FOUND` too: the guard answers before the facade.
- The key writes a new id, then the same document again, and each time the document reads back in `notes` with the content sent.
- The operator's unconfined key rewrites the document of `secrets`.

The test runs the real ingest with the package's fake embedder. `newPolicyConn` takes options for the database, so the test can pass `cortexdb.WithEmbedder`.

**Failing first.** On `main`, the test fails: `InsertGraphDocument over another collection's document: <nil>, want NOT_FOUND "knowledge \"sec\" not found"` and `the document is now "Overwritten by notes." in "notes", want it untouched`. Six hand mutations, six killed: the guard not called, the guard called without the request's id, the guard's refusal ignored, the guard skipped for empty content, the document created outside the collection asked for, and every named write refused, the key's own included. Every line of the patch has a test.

## Performance Impact
For a confined key, one `GetKnowledge` per `InsertGraphDocument` that names an id, and two when the id names nothing (the guard reads again to tell a create from a foreign row); `GetKnowledge` loads the document's chunks, so its cost grows with the document. Nothing for an unconfined key.

## Breaking Changes
None for an unconfined key. A confined key that named a document outside its scope in `InsertGraphDocument` now gets `NOT_FOUND` instead of overwriting it.
