## Description

The gRPC request log (`pkg/rpcserver/trace.go`) names the method, the key and the tool of each call. It does not say which rows a call named. On a shared brain the next question after "which key called `knowledge_get`" is "which document", and the trace file had no answer.

The allowlist already declares, tool by tool, the argument paths that name rows (`toolRule.ids`), and `JSONPathValues` reads them. Two more paths name rows but are classified as data, so the guard does not load them: `memory_ids` of `memory_get`, and `plan.filters.document_ids` of the search tools.

### Change
- `authz.RowIDsOf(tool, args)` returns the ids a call names, by path: the values at the tool's `ids` paths, plus `memory_ids` and `plan.filters.document_ids` when the tool takes them (`rowData`, one declared list). It reads arguments only, for any key, and decides nothing. A tool off the allowlist gives nil: no guess from field names.
- The request log fills a new `ids` field of the JSON record with it, for a `CallTool`. A call that names no row has no `ids` field (`omitempty`), so the record of every other call is as on `main`.
- The text line gains ` ids=<n>`, the number of ids, after `tool=`, and only when there are some. The ids themselves go to the trace file only, so a `memory_get` of fifty ids does not fill the standard log.
- A denied call keeps its ids: the record says what the key reached for.
- Access does not change for any tool. Only the log changes.

### Tool by tool: paths logged

| Tool | Paths logged |
| :- | :- |
| `ingest_document` | `document_id` |
| `knowledge_save`, `knowledge_update`, `knowledge_get`, `knowledge_delete` | `knowledge_id` |
| `memory_save` | `memory_id`, `supersedes` |
| `knowledge_memory_remember`, `memory_update`, `memory_delete` | `memory_id` |
| `memory_get` | `memory_id`, `memory_ids` |
| `knowledge_search`, `search_text`, `search_graphrag_lexical`, `memory_search`, `knowledge_memory_recall`, `knowledge_memory_build_context_pack` | `plan.filters.document_ids` |
| `search_vector_range`, `aggregate_metadata`, `representative_records`, `extract_conversation` | none |
| any tool off the allowlist | none (no `ids` field) |
| any RPC other than `CallTool` | none |

### Scope
- gRPC only. The REST port has no request log; adding one is another change.
- The ids a tool returns (the hits of a search) are not logged. That is a different rule.
- Keys of an open filter map (`filters.document_id` of `aggregate_metadata`) are data and are not read.

### Tests
`pkg/authz/row_ids_test.go`:
- `TestRowIDsOfReadsEveryDeclaredPath`: the table above, as `loggedPaths`, for every tool of the allowlist. Arguments carry a value at each path (two ids in an array for the list paths), plus a `foo_id` and a `metadata.document_id` that must not be taken. A tool added to the allowlist without a row in the table fails.
- `TestRowIDsOfTakesNothingOffTheAllowlist`: `graph_cypher_query` with a `document_id`, `knowledge_memory_consolidate` with `promotion.memory_ids`, arguments that are not JSON, an empty id and an empty list give nil; `Knowledge_ID` is read as `knowledge_id`, as `encoding/json` reads it.
- `TestEveryArgumentThatNamesARowIsLogged`: every argument of the allowlist whose name ends in `_id` or `_ids`, or is `supersedes`, is logged or listed with a reason (`session_id` and `plan.filters.session_id` name a bucket, `plan.filters.user_id` is a scope field). A row-naming argument added later as data fails here.

`pkg/rpcserver/trace_ids_test.go`:
- `TestTheRecordNamesTheRowsTheCallNames`: through the log and the auth interceptor, `knowledge_get`, `memory_get` with a list, `memory_save` with `supersedes`, a pinned `knowledge_search` and a denied `ingest_document` carry their ids in the record and ` tool=<name> ids=<n>` on the line; an unpinned search and `graph_cypher_query` with a `document_id` have no `ids` field and no count.
- `TestAnotherMethodLogsNoIDs`: a `SearchMemory` record has no `ids`.

**Failing first.** On `main`, `TestTheRecordNamesTheRowsTheCallNames` fails (`knowledge_get {"knowledge_id":"k1"}: ids <nil>, want map[knowledge_id:[k1]]`, and the line lacks ` ids=1`). The `pkg/authz` tests call the new `RowIDsOf` and do not compile there. Each rule then has a hand mutation that a named test catches, nine in all, nine killed: `rowData` not read, `memory_ids` or `plan.filters.document_ids` taken out of it, the guarded ids not read, a `document_id` guess for a tool off the allowlist, the record's field never filled, no count on the line, the count of paths instead of ids, an empty entry kept for a path with no id. Every line of the patch has a test. To replay the first part: post `pkg/rpcserver/trace_ids_test.go` on `main` and run `go test ./pkg/rpcserver/ -run TestTheRecordNamesTheRowsTheCallNames`.

## Performance Impact
Only for a call that is logged (`CORTEXDB_TRACE=1`, or a slow call): one more decode of the `CallTool` arguments, after the call returns. Nothing for a call that is not logged. The record grows with the ids a call names; a `memory_get` of many ids writes them all to the trace file.

## Breaking Changes
None. The JSON record gains an optional `ids` field, and the text line gains ` ids=<n>` after `tool=` when a call names rows. A parser that splits the line on spaces and reads `key=value` pairs is not affected.

## Questions
1. Should the text line carry the ids themselves rather than their count? I kept the count so that the standard log stays one short line per call.
2. Should the record have a bound on the number of ids, for a `memory_get` of thousands?
