## Description

The coverage floor of v2.138.0 (`lexical_rarity.go`) compares the words of the question with the row's words with their accents. On SQLite the word index (FTS5 `unicode61`) folds accents. So a row that the index finds for a query typed without accents is then dropped by the floor. `SearchKnowledge("universitat zurich recht")` returned `[]` over a row "Die Universität Zürich untersteht dem kantonalen Recht…", which `search_text` finds. The same holds the other way round ("état exécutif" over "Etat … executif"), and for memories.

### Fix
Coverage compares words without their accents, as the index reads them (`pkg/cortexdb/lexical_rarity.go`):
- `foldAccents` removes accents from lowercased text. An accented Latin letter (U+00E0 to U+017F) becomes the letter itself ("é" → "e", "ü" → "u", "ſ" → "s"). A combining mark (U+0300 to U+036F) goes. Letters that are not an accented form of another ("ß", "æ", "ø", "ł", "œ") stay. This is the set FTS5 `unicode61` folds: I checked each rune from U+00C0 to U+017F against the index (modernc.org/sqlite v1.38.2, via `fts5vocab`). It needs no new dependency. An ASCII string is returned unchanged with no allocation.
- `coverage` folds the row once and compares it with the folded words of the question and of its synonyms (keywords, alternate queries), computed once per scorer.
- `newRarityQuery` drops a synonym that is a question word with other accents ("liberte" beside "liberté"), as it drops one with the same spelling. Otherwise the row would be credited twice for one word.
- `containsWord` is unchanged.

The document frequencies still count the spelling typed: the count is one `LIKE` scan, which keeps accents. A word typed without accents is then counted only in rows that spell it so, and weighs as a rare word. I left this as it is: folding the count would need a fold in SQL on both engines (see Questions).

### Scope
SQLite only. PostgreSQL's `to_tsvector('simple', …)` keeps accents, so its index does not find the row in the first place. That is a separate question (below), not this PR.

### Tests

- `TestKnowledgeKeywordFloorStillRefusesOneSharedWordWithoutAccents`: a row sharing one word of three, with or without accents, is still refused, and so is a question about nothing stored.

## Performance Impact
One extra pass over each candidate row's lowercased text, only when the row holds a non-ASCII byte. The folded question words are computed once per search.

## Breaking Changes
None. On SQLite, rows the index finds for a query typed without accents (or with accents over unaccented text) are no longer dropped by the floor.

## Questions
- PostgreSQL: `to_tsvector('simple', …)` keeps accents, so the index there does not find "Universität" for "universitat" in the first place, and the document-frequency `ILIKE` keeps them too. The usual fix is the `unaccent` extension (and a text search configuration built on it), which some managed instances do not offer. Do you want it, and should it be optional?
- The document frequencies count the spelling typed (above). Do you want them folded too? It would need a fold in SQL on both engines, so it belongs with the question above.
