## Description

`cortexdb-grpc` reads its key file (`-keys`, `CORTEXDB_KEY_FILE`) once, when it starts, and so does its REST face (`-http`): `rpcserver.NewWithPolicy` and `httpapi.NewWithPolicy` call `authz.Resolve` and capture the key set. A key removed from the file keeps working until the server restarts, and a key added to it is refused until then. Revoking a key means restarting the brain everybody shares.

With this PR, a server built on a key file applies the file as it stands at each request: a key added is served and a key removed is refused, without a restart. `cmd/cortexdb-grpc` needs no change, since both faces already take the path through `Options.KeyFile`.

Independent of the other open PRs: based on `main`, touches `pkg/authz`, `pkg/rpcserver`, `pkg/httpapi`, and one sentence in `docs/GUIDE.md` and `SKILL.md`. 184 lines outside tests and docs over 7 files, 16 removed; 141 of them are `pkg/authz/key_source.go`, comments included.

### Fix
`authz.KeySource` (`pkg/authz/key_source.go`) serves the keys of a key file:
- `OpenKeySource(path)` loads the file once; the first load must succeed, with the errors `Load` gives. A server whose file does not load at start still refuses everything, as on `main`.
- `Current()` stats the file, outside any lock, and compares time, size and `os.SameFile` with the last read. Unchanged, it returns the key set it holds, through an `atomic.Pointer`. Changed, it takes a mutex, reads the file, and parses it only when the text differs from the text of the keys in force. `os.SameFile` catches a file replaced by rename with the same size and time.
- A change that does not load (unreadable, broken JSON, an unknown field, `{"keys":[]}`, an empty file, the file removed) leaves the keys in force. It is reported once per failed change, through `KeySource.Warn`, or `log.Printf` when `Warn` is nil. A file read but not parsed is not read again until it changes. A second failed change after a success is reported again.
- `StaticKeySource(keys)` serves a key set and reads no file. `ResolveSource(keyFile, token)` is `Resolve` for a server that keeps running: a key file is the whole policy and is reread; without one, the legacy token, fixed.

Wiring:
- `rpcserver.NewWithPolicy` and `httpapi.NewWithPolicy` take their keys from `ResolveSource`, and the interceptor and the REST `authenticate` call `Current()` at each request.
- `Options.Keys` is unchanged: a key set given in process takes precedence and is never reread. `rpcserver.AuthInterceptor(*authz.KeySet, db)` is unchanged and static. `rpcserver.AuthInterceptorFromSource(*authz.KeySource, db)` is new, for a process that mounts `cortexdb.v1` on a server of its own and wants the reread too.
- `authz.Load` and `authz.Resolve` are unchanged.

### Limits
- A file rewritten in place with the same size, within the same tick of the file system clock, is not seen until its next change. A write by rename (temporary file, then `os.Rename`) is always seen, through `os.SameFile`.
- `cortexdb-grpc -http` opens one source per face on the same path, so a failed change is logged twice, once per face. Each request goes through one face, so one stat per request. Sharing one source would need a new field in `Options`; I left it out.
- A file caught half-written fails to parse: the previous keys stay, one warning, and the next stat sees the final size and reads it again.

### Behaviour change
A valid key file now applies as soon as it is written. An operator who edited the file ahead of a planned restart will see the change at once. No signature changes.

### Questions
1. A change that does not load keeps the previous keys and logs. The other choice is the start-up rule: refuse every call until the file loads again. Keeping the keys avoids locking everybody out on a typo; refusing is closer to what `New` does at start. Which do you prefer?
2. The stat on every request costs about 3 µs (below). If that is too much on the hot path, a minimum interval between two stats (one second, compared in an atomic, no goroutine) brings it to a few tens of nanoseconds, at the price of up to one second before a revocation applies. I can add it here or later.
3. `docs/GUIDE_CN.md` carries the same paragraph as `docs/GUIDE.md`; I did not touch the Chinese text.

## Performance Impact
One `os.Stat` of the key file per request, on servers built with a key file. Nothing for `Options.Keys`, a token, or no auth. Apple M2, Go 1.26.5, darwin/arm64, file in a temp dir (APFS), `go test -run '^$' -bench 'KeySet|KeySource' -benchmem -count=5 ./pkg/authz/`:

| Benchmark | ns/op | B/op, allocs |
| :- | -: | :- |
| `KeySet.Lookup`, 2 keys | 20.9 to 22.7 | 0, 0 |
| `KeySource.Current().Lookup`, 2 keys | 3,360 to 4,921 | 320, 2 |
| `KeySet.Lookup`, 8 goroutines | 4.0 to 8.2 | 0, 0 |
| `KeySource.Current().Lookup`, 8 goroutines | 2,264 to 3,446 | 320, 2 |

The two allocations are the `os.FileInfo` of the stat. The stat is outside the lock, so parallel requests do not queue on it: a first version that held the mutex during the stat measured about 7.4 µs/op with 8 goroutines, against 2.3 to 3.4 µs here.

One authenticated `Admin.Health` over bufconn, `go test -run '^$' -bench HealthWith -benchmem ./pkg/rpcserver/`, six interleaved runs of 2 s each: 41.0 to 47.6 µs with `Options.Keys`, 44.9 to 67.0 µs with a key file. The machine was loaded (load average about 15 on 8 cores), so these two ranges are noisy; on a quiet run of the same machine an earlier measure gave about 20 to 27 µs for the call and about 3 µs for the stat. Calls that search or write cost hundreds of microseconds or more.

## Breaking Changes
None in the API. A server built with `KeyFile` now applies a valid change to the file without a restart (see "Behaviour change").
