## Description

Under a `CallerScope`, the graph tools served documents and memories outside the scope. A caller confined to collection `alpha` got, from `expand_graph`, `get_nodes`, `knowledge_memory_neighbors`, `knowledge_memory_shortest_path`, `search_paths`, `search_chunks_by_entities` and `knowledge_memory_expand_entity_context`: the chunk text of another collection, its chunk and document nodes, the relations only that collection backs, and the memory text of another user. `CallerScope.Knowledge` was read by `SearchKnowledge` alone, and `hiddenMemoryNodes` looked at the review gate only.

Based on `main`. Touches `pkg/cortexdb` only. No port changes: the allowlist still refuses these tools to a confined key, so today this concerns an embedded library or a server that sets a `CallerScope` itself. Two PRs are stacked on this one: the entity rule (GC-15) and the allowlist (GC-16).

### Fix

The rule goes through the choke point that already hides expired documents and documents the review gate holds, `hiddenAmong` (`pkg/cortexdb/expiry.go`):

- Under a scope with a `Knowledge` rule, `hiddenAmong` also hides the documents the rule does not reach (`outOfScopeDocuments`). The `documents` table has no collection: a document is in the collection of its chunks, on `embeddings.collection_id`. One query reads the collection of every chunk of the documents met (`documentCollectionsQuery`). A document is out of scope when one of its chunks is in a collection the rule refuses, or when it has no chunk, since then nothing says which collection it is in (`outOfScope`).
- The scope adds to the expiry and the review gate, it does not replace them. When the documents table cannot be read, the expiry stays advisory, as on `main`, and the scope still applies. When the collections cannot be read, every document met is hidden: the scope fails closed, like the review gate.
- Under a `Memory` rule, a walk leaves out a memory node whose bucket the rule refuses (`hiddenMemoryNodes`, `memoryNodeShown`, through `memoryReadPermitted`). A memory that cannot be read is hidden, as under the review gate.
- The graph tools inherit it through the paths they already take: `withoutExpiredDocuments` (nodes, and the edges that touch a hidden node), `withoutExpiredProvenance` (an edge only hidden documents back is left out; an edge that cites a chunk of each collection keeps the permitted one) and `loadToolChunks` (chunk text).
- Without a caller scope, or under a scope with no rule, nothing is read and nothing changes.

### Scope

- `find_nodes` passes no hidden-node filter today, for the expiry either. Its own PR (gc-13, "find_nodes leaves out the hidden nodes") routes it through `withoutExpiredDocuments`; with it merged, `find_nodes` inherits this rule like the others. Until then its row in the class test is skipped, with that reason.
- `hiddenAmong` is shared with the search paths (`filterScoredEmbeddings`, `chunksInScope`). Under a knowledge rule they hide out-of-scope documents too. For a confined key the ports already force the collection on those tools, so their answers do not change.
- Entities are not filtered here, and a walk can still start from a hidden node. GC-15, stacked on this PR, does both.

## Performance Impact
Under a knowledge rule, one more query per `hiddenAmong` call: the collections of the documents met, through `idx_embeddings_doc_id` and the primary key of `collections`. Under a memory rule, one memory row read per memory node a walk meets, as the review gate already does. Nothing without a caller scope.

## Breaking Changes
None without a caller scope. Under a `CallerScope` with a knowledge rule, the graph tools and the search paths leave out the documents of a collection the rule refuses, and the documents with no chunk; under a memory rule, a walk leaves out the memories of a bucket the rule refuses.

## Questions
1. A document whose chunks are in two collections is hidden unless every one is permitted. Should one permitted chunk be enough?
2. A document with no chunk is hidden under a knowledge rule, since nothing says its collection. Is that the rule you want?
