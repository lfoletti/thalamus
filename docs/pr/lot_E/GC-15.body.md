## Description

Stacked on GC-14 (under a caller scope, the graph tools leave out the documents and memories outside it); the diff below is the one commit on top of it.

With GC-14, a caller confined to collection `alpha` no longer gets beta's chunks, but still gets beta's entities. Entity nodes are shared across collections, keyed by name, and a graph tool served them whole: an entity only beta's text mentions (Project Nightjar, and the words the ingest makes entities of), the description beta wrote last on an entity both collections know, the `collections` list that names beta, and `source_document_ids`. A walk could also start from a node the scope hides, and its answer then told what that node links to: `expand_graph` from beta's chunk returned the entities it mentions, `search_chunks_by_entities` from Project Nightjar at three hops reached alpha's chunk through beta's relation, `search_paths` resolved a hidden seed.

Touches `pkg/cortexdb` only, as GC-14 does.

### Fix

- **Entities.** Under a knowledge rule, `withoutExpiredDocuments` serves an entity, or any node other than a chunk, a document or a memory, only when a collection in its `collections` list (written since #70) is permitted, and then as a copy with its id, its name, its type and nothing else (`scopedNode`, `pkg/cortexdb/entity_collections.go`): the description is the last writer's, whichever collection that was, and the other properties and the vector come from the same writes. The stored node is not changed. A node with no list is not served (see Questions). Chunk, document and memory nodes keep the rules of GC-14. An edge that touches a hidden entity is left out with it, as for a hidden chunk.
- **Seeds.** Under any scope rule, a walk starts only from the seeds the scope serves (`servedSeeds`): `expand_graph`, `search_chunks_by_entities`, `knowledge_memory_neighbors`, and through them `knowledge_memory_expand_entity_context`. A hidden seed answers as a seed that does not exist: no node, no chunk, no neighbour. When the seeds cannot be read, none is walked from. `search_paths` reports a hidden seed under `unresolved`, as it reports one that does not exist. `knowledge_memory_shortest_path` already answers "no path found" when a node of the path is hidden, and now returns the reduced nodes.
- Without a caller scope, or under a scope with no knowledge rule, entities are served whole; without any rule, seeds are not read.

### Scope

- A walk still runs on the stored graph. A node reached only through a hidden node is served when the scope serves it, cut from the hidden one, as a longer live path is not looked for after an expiry (`ShortestPath`). Making the traversal itself scope-aware is in `pkg/graph`, a larger change.
- Edges keep their own properties: provenance is filtered by GC-14, free relation metadata is served as written. An edge with no provenance between two served entities is served.
- `find_nodes` inherits the entity rule once it passes the hidden-node filter (gc-13), as in GC-14.

## Performance Impact
Under a scope rule, one `GetNodesBatch` of the seeds per walk, and the checks of GC-14 on them. Reducing an entity copies the node. Nothing without a caller scope.

## Breaking Changes
None without a caller scope. Under a knowledge rule, an entity no permitted collection lists is not served, and a served entity has its name and type alone. Under any scope rule, a walk from a hidden node answers as from a node that does not exist.

## Questions
1. **An entity with no `collections` list**, written by `upsert_entities`, by a memory, or before #70. The walk gate of #70 takes it as known everywhere. Under a caller scope this PR takes it as known nowhere, the safer reading: nothing says which collection wrote it. Consequences: under a knowledge rule, the entities of memories and the nodes other tools write (decisions, runs) are not served; a user-confined key, whose knowledge rule refuses every collection, is served no entity at all. Should a caller scope keep the #70 reading instead, or serve such an entity only when a visible chunk or memory mentions it?
2. A knowledge rule that permits every collection an entity lists still reduces it, since the node does not record which write set the description. Would you rather serve it whole in that case?
3. Free relation metadata on an edge between two served entities is served as written. Should a scope reduce edges the same way?
4. A node reached only through a hidden node is still served, cut from it (see Scope). Is that acceptable for now, or do you want the traversal confined first?
