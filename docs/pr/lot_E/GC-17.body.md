## Description

The graph lane of `db.Query` (`cortex_query`, `POST /v1/query`) walks the shared graph from the named entities, up to `prefetch[].max_hops` edges, and since #78 keeps only the chunks of the collection queried. The walk itself was not confined: it started from an entity only another collection knows, followed relations only another collection states, and passed through another collection's chunks and through memories. A chunk of the collection reached that way tells the caller that the other collection's entity or relation exists.

With two collections, `alpha` and `beta`, and a relation `Kestrel Vale -funds-> Project Nightjar` that only `beta` states, a query on `alpha` seeded with `Project Nightjar` (an entity only `beta` knows) and `max_hops: 2` returns `alpha`'s chunk about Kestrel Vale. `POST /v1/query` serves that to a key confined to `alpha`, which may call the route on its collection. No text of `beta` comes back; the structure does.

Independent of the other open PRs: based on `main`, `pkg/cortexdb`, with a REST test in `pkg/httpapi`: 221 lines outside tests over 3 files (one new), 56 of them comments or blank, 5 removed.

### Fix
With a collection, the graph lane walks only what the collection may see (`neighborsInCollection`, `pkg/cortexdb/query_graph_scope.go`). It is `graph.Neighbors` in both directions, breadth first, with the same depth, limit and node types, and one rule for each step (`laneScope.mayEnter`):
- The node must be a chunk or a document of the collection, or an entity the collection knows (`entityKnownIn`, the rule of #70). The seed itself must be an entity the collection knows.
- A memory node is never entered: no collection holds it.
- An edge that names its provenance (`document_id`, `chunk_ids`, `source_chunk_id`) must name a document or a chunk of the collection. An edge that names none, such as a relation written by `upsert_relations` without them, is followed, as an entity with no list is known everywhere since #70.
- A document is the collection's when it has a chunk in the collection (`documentsInCollection`, one query per round of the walk, on `embeddings` joined to `collections`). When the collections cannot be read, the walk fails with `load walked chunks`, as `chunksInScope` does.

Without a collection the lane walks the whole graph with `graph.Neighbors`, as before. The tool `search_chunks_by_entities` is unchanged: it has no collection.

### Scope
- The walk passes through a hidden chunk as before; the lane leaves hidden chunks out of what it returns (`loadToolChunks`, `chunksInScope`).
- The expansion of `knowledge_search` in graph mode (#70) checks the entities it walks through, not the provenance of relations, and walks through memory nodes. I left it as it is; it can take the same rule if you want both walks to agree (Questions).
- With this merged, a key confined to a collection could also send `prefetch[].max_hops` to the tool `cortex_query`. #<GC-18> opens the tool with `max_hops` refused; a later change can allow it.

## Performance Impact
With a collection only: per round of the walk, one read of the node summaries (`graphNodeSummariesByIDs`) and one query on `embeddings` for the documents met, on top of the edges `graph.Neighbors` already reads. A round is one hop; the default is one hop. Nothing changes without a collection.

## Breaking Changes
A query with a collection whose graph lane reached its chunks only through another collection's entities, relations or chunks, or through a memory, no longer returns them. Without a collection, nothing changes.
