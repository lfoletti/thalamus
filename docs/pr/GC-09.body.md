## Description

### Problem
A `graph`-mode search confined to one collection can return another collection's chunks. An entity node is one per name across the whole brain. So the walk from a chunk in `notes` to the entity "Acme", and from "Acme" to every chunk that mentions it, reaches chunks in `secrets`. The `lexical`, `auto` and `ppr` modes keep to the collection; `graph` did not. A test that ingests the same entity name in two collections and searches one of them in `graph` mode gets the other collection's chunk back.

### Fix
Two changes in the neighbourhood expansion:
- Chunk neighbours are checked against the searched collection the way the seeds already are (`chunksInScope`), so a chunk from another collection is never added.
- Entity nodes record the collections whose chunks mention them, in a property `collections` kept as a union by `ingest_document` and `knowledge_save`. The walk keeps to entities the searched collection knows.

An entity with no `collections` list, because it is older or was written by `upsert_entities`, which has no collection, is known everywhere, as before. An unconfined search (no collection) is unchanged. Deleting a document does not shrink an entity's list; the list only widens, and the chunk check above is what keeps the result correct.

### Tests
- New `pkg/cortexdb/entity_collections_test.go`: the union logic, and the leak itself: two collections share an entity, a `graph` search of one returns only its own chunk. The test fails before the change.
- `go vet` and `go test -race ./...` pass; `TestLexicalRetrievalQuality` unchanged.
