## Description

The third way out you found on #72, fixed where it lives rather than in the rules: the graph lane of `cortex_query` now stays in the collection the query names. Independent of #72 to #74; until it lands, the allowlist of #72 keeps `cortex_query` off the tools a confined key may call, and a follow-up adds it once this is in.

### Problem
`cortex_query` with a graph prefetch calls `SearchChunksByEntities` without the collection. Entity nodes are shared by every collection, so `{"collection":"notes","entity_names":["Orpheus"]}` returned a chunk of `secrets` that mentions Orpheus.

### Fix
`runGraphQueryPrefetch` takes the request's collection and, when one is set, keeps only the chunks that sit in it, through `chunksInScope`, the same check the graph expansion applies to its neighbours (`graph_runtime.go`). A query without a collection searches the whole brain, as before. When the chunks' collection cannot be read, the query fails rather than serve them.

### Tests
- `pkg/cortexdb/query_prefetch_scope_test.go`: two documents that mention the same entity, one in `notes` and one in `secrets`; a query on `notes` through the graph lane serves `notes` only; a query with no collection serves both; with the `collections` table unreadable (column renamed), the query fails with the read error.
- `go vet` and `go test -race ./...` pass.

**Failing first.** The test fails on `main`: the query on `notes` serves both documents. Four mutations, four killed: the collection ignored; the chunks outside the collection kept and the others dropped; the read error ignored; the collection not handed to the lane. Every line of the patch has a test.

Part of a small series on running one CortexDB server for several teams (see discussion #66, batch 2).
